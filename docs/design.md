# Design notes

Short rationale for the decisions that shaped this harness — the kind of trade-offs an
applied-agent team reasons about daily.

## 1. Benchmark-agnostic core

The agent only ever sees an `Environment` (`exec` + `get_patch`) and a `Task`
(problem statement). Both the synthetic local benchmark and SWE-bench implement the same
`BenchmarkProvider` interface. Consequences:

- The **agent loop, trajectory logging, failure taxonomy, and metrics are written once** and
  reused across benchmarks.
- New benchmarks (e.g. a bug-fix set scraped from your own repos) are a single new provider.
- Development doesn't block on Docker: the local provider validates the entire pipeline in
  seconds, then SWE-bench plugs into the identical downstream code.

## 2. Failure taxonomy over raw solve rate

A single pass/fail number tells you *that* an agent failed, not *why*. The taxonomy
(`no_edit`, `patch_apply_failed`, `wrong_fix`, `max_steps`, `protocol_violation`,
`eval_timeout`) maps each failure to the intervention that would fix it — localization vs.
edit-formatting vs. reasoning vs. planning. This is the difference between "the score went
down" and "retrieval regressed localization; here's the evidence."

## 3. One lever per condition

Every behavioral knob lives on `AgentConfig`, and each ablation condition differs from the
baseline by exactly one field. Any solve-rate change is therefore attributable to that lever.
This is what lets the harness make *causal* statements ("the run_tests tool is worth +33
points for a 1.5B model") rather than correlational ones.

## 4. Provider-agnostic model access

`LLMClient` speaks the OpenAI chat API. The default `base_url` is a local Ollama server (free,
offline), but pointing at any OpenAI-compatible endpoint is a one-line config change. Dev on a
fast small model, produce headline numbers on a bigger one, no code changes.

## 5. Reproducibility

Each run persists its full config, per-task trajectories, and metrics under
`results/<run_name>/`. The benchmark is deterministically regenerated by a script and
validated (every buggy workspace must fail its own oracle). Temperature defaults to 0.

## Known limitations

- The local benchmark is intentionally small and single-file; it exists to exercise the
  harness and study scaffolding cheaply, **not** to be a hard capability benchmark. SWE-bench
  Verified is the capability yardstick.
- Best-of-N uses independent rollouts with a fresh environment each; it does not share
  information across attempts (no reflection/repair loop — a natural next lever).
- Patch application in the local provider falls back from `git apply` to `patch -p1`, which is
  lenient; SWE-bench uses the official, strict harness.
